# План реализации: от текущего состояния до полного паритета и сверх него

Основание — `docs/feature-review.md` (сравнение с OpenLDAP, ApacheDS, Samba AD, 389 DS) и
`docs/password-hashing.md`. Сделано ранее: конфигурация, модель, каталог, бэкенды `file`/`null`,
BER-кадрирование, bind, search с фильтрами и пагинацией, парольные схемы с политикой, ACL, отказ
простого bind без шифрования.

Правила работы (ub-mode): каждый пункт — отдельный проверенный шаг и отдельный коммит; тест пишется
раньше кода там, где поведение новое; расхождение с gorestldap фиксируется в `docs/ub-log.md` с
причиной; `clippy -D warnings` и `fmt --check` — часть определения «готово».

## Фаза A. Сервер обслуживает трафик

Без этого фазы B-D проверить нечем: `main` сейчас только печатает конфигурацию.

| # | Шаг | Зачем | Готово, когда |
|---|---|---|---|
| A1 | Слушатель и цикл соединения | Диспетчер `handle` не связан с сокетом | `ldapsearch` получает ответ от живого процесса; тест на два сообщения в одном соединении, на unbind и на обрыв клиента |
| A2 | LDAPS и StartTLS на rustls + rustls-rustcrypto | Без TLS сервер лабораторный; StartTLS нужен клиентам без LDAPS-порта | Тест с самоподписанным сертификатом (`rcgen`) проходит bind и search по TLS; `use_tls: false` + StartTLS не ломает соединение |
| A3 | Перезагрузка данных: таймер, `SIGUSR1`, HTTP `HEAD /callback` с токеном | Паритет с gorestldap; без этого правка данных требует рестарта | Тест: после `SIGUSR1` и после callback в каталоге видны новые записи; неверный токен — 401 |
| A4 | Плавная остановка по `SIGTERM`/`SIGINT` | gorestldap умеет, иначе соединения рвутся на середине ответа | Тест: начатая операция дописывается, новый accept не принимается |

## Фаза B. Запись

| # | Шаг | Зачем | Готово, когда |
|---|---|---|---|
| B1 ✅ | Операционные атрибуты: `createTimestamp`, `modifyTimestamp`, `creatorsName`, `modifiersName`, `entryCSN` | Аудит и инкрементальная выгрузка; их спрашивают все клиенты | Отдаются по `+` и явному имени, не отдаются по `*`; значения меняются при записи |
| B2 ✅ | Полный `modify`: add / delete / replace для одного и нескольких значений | сделано: путь записи «мутация → бэкенд → перезагрузка снимка», 400 тестов, живые `ldapmodify` |
| B3 | Assertion control (1.3.6.1.1.12) и permissiveModify | Защита от гонок: «запиши, если значение всё ещё то» | Тест: при несовпадении — `assertionFailed`, данные не изменились |
| B4 | `add` / `del` / `modifyDN` | Каталог только читается; нельзя завести пользователя | Тест: создание и удаление пользователя, отказ удалять непустой узел (`notAllowedOnNonLeaf`), переименование меняет DN и `entryUUID` не теряется |
| B5 ✅ | Проверка схемы минимум: обязательные и разрешённые атрибуты по `objectClass` | Отсекает мусор, делает поведение предсказуемым | Тест: `inetOrgPerson` без `sn` и `cn` отвергается `objectClassViolation`; лишний атрибут — `objectClassViolation` |
| B6 | Обновление слабого хеша при успешном bind | Единственный момент, когда пароль известен в открытом виде | Тест: `{SSHA}` после bind заменяется на Argon2id через бэкенд; при выключенной опции — не меняется |
| B7 | Уникальность (`cn`, `uid`) и ссылочная целостность (`memberUid`) | Дубли ломают bind и поиск, «висячие» члены — группы | Тест: загрузка данных с дублем даёт ошибку с именами; удаление пользователя чистит `memberUid` |

| # | Шаг | Зачем | Готово, когда |

| # | Шаг | Готово, когда |

## Порядок и зависимости

A1 → A2 → A3 → A4 → B1 → B2 → B3 → B4 → B5 → B6 → B7 → C1 → C2 → C3 → C4 → C5 → D1 → D2 → D3 → D4.

Исключение из порядка (записано осознанно): B2 сделан раньше B1. Операционные атрибуты
(`modifyTimestamp`, `entryCSN`, `modifiersName`) имеют смысл только тогда, когда есть запись,
которая их меняет; до B2 их пришлось бы выдумывать при загрузке. B1 ставится сразу после B2 и
опирается на уже работающий путь записи.

Зависимости, которые нельзя нарушать: A1 раньше всего (иначе нечего проверять снаружи); B1 до B2
(запись должна быть аудируемой сразу); B5 после B4 (схему проверять на создании, а не только на
изменении); B7 после B4 (целостность проверяется на удалении); C1 после B5 (публиковать нечего,
пока нет реестра схемы); D1 в конце фазы C (мерить имеет смысл законченный сервер).

## Что сознательно не делаем

- Kerberos/KDC и AD-эмуляция (DRS, `objectSid`): это отдельный продукт, а не фасад над REST.
- Мультимастер-репликация: модель «несколько серверов читают один источник» уже работает;
  Content Sync (RFC 4533) — кандидат после C5, не раньше.
- X.500-ACI ApacheDS и `sock`/`dnssrv`-бэкенды OpenLDAP: сложность без выгоды для нашей задачи.

## Фаза E. Модель данных, схема, индексы (добавлена после обсуждения)

Подробности и замеры — `docs/storage-schema-indexing.md`. Порядок жёсткий: индексы строятся по
атрибутам, атрибуты появляются из обобщённой модели записи и схемы.

| # | Шаг | Зачем |
|---|---|---|
| E1 ✅ | Обобщённая запись `Entry` (DN + произвольные атрибуты) + адаптер текущего JSON | сделано: поиск на 20 тыс. ускорился в 6–8 раз, память 309 байт на запись |
| E2 ✅ | Реестр схемы: разбор RFC 4512, встроенная `core`, MUST/MAY/SINGLE-VALUE/синтаксисы, режимы strict/warn/off | типы атрибутов нужны индексам, сортировке и проверке записи |
| E3 ✅ | Индексы `pres` и `eq` с конфигурацией и тестами эквивалентности перебору | сделано: 20 тыс. — 8.9→2.7 мс на равенство, 1.1 МБ индекса |
| E4 | Индексы `sub` (3-граммы) и `ord` (диапазоны) | подстроки, база для server-side sort и VLV (C2) |
| E5 | Переиндексация: `POST /reindex`, `--check-index`, `--reindex` | эксплуатация без перезапуска |
| E6 | Схема на ходу: `/schema/reload`, `SIGUSR2`, отключение наборов, изменение через `cn=schema` | добавление и выключение схем без рестарта |
| E7 ◐ | Бэкенд `redb` (ACID, одна транзакция на набор изменений) и LDIF-выгрузка | `redb` сделан; LDIF перенесён сюда из D4 и делается до фазы D — выгрузка нужна раньше, чем упаковка и метрики, иначе каталог нечем обменять с OpenLDAP |

Фаза E идёт после B (запись) и до C: шаги B5 (проверка схемы) и C1 (публикация `cn=schema`)
поглощаются E2 и E6, потому что писать схему под зашитые структуры значило бы переписывать её
сразу после E1.
