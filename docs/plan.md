# План реализации: от текущего состояния до полного паритета и сверх него

Основание — `docs/feature-review.md` (сравнение с OpenLDAP, ApacheDS, Samba AD, 389 DS) и
`docs/password-hashing.md`. Сделано ранее: конфигурация, модель, каталог, бэкенды `file`/`null`,
BER-кадрирование, bind, search с фильтрами и пагинацией, парольные схемы с политикой, ACL, отказ
простого bind без шифрования.

Правила работы (ub-mode): каждый пункт — отдельный проверенный шаг и отдельный коммит; тест пишется
раньше кода там, где поведение новое; расхождение с gorestldap фиксируется в `docs/ub-log.md` с
причиной; `clippy -D warnings` и `fmt --check` — часть определения «готово».

## Порядок и зависимости

A1 → A2 → A3 → A4 → B1 → B2 → B3 → B4 → B5 → B6 → B7 → E1 → … → E7 → C1 → C2 → C3 → C4 → C5 →
F1 → F2 → F3 → F4 → F5 → D1 → D2 → D3 → D4.

Исключение из порядка (записано осознанно): B2 сделан раньше B1. Операционные атрибуты
(`modifyTimestamp`, `entryCSN`, `modifiersName`) имеют смысл только тогда, когда есть запись,
которая их меняет; до B2 их пришлось бы выдумывать при загрузке. B1 ставится сразу после B2 и
опирается на уже работающий путь записи.


Вопрос о формате данных (обсуждён после C2): **LDIF остаётся форматом выгрузки** — его читают
`ldapadd`/`slapadd`, и в этом его единственная ценность. YAML как замена LDIF сузил бы обмен до
«понимаем только мы». Решение: **YAML сделан вторым форматом выгрузки** (E8, `--export-yaml`),
LDIF остаётся первым. Для «каталог как код в git» по-прежнему возможен отдельный **JSONL-бэкенд**
(одна запись — одна строка: потоковое чтение, построчный diff, отсутствие неявной типизации YAML,
из-за которой `uid: no` становится `false`, а `roomNumber: 012` — числом 10). YAML как входной
формат для ручной правки — по желанию, поверх JSONL.

Пробел, найденный при живой проверке C1: **bootstrap**. Пустой каталог нельзя наполнить — `add`
требует bind, bind требует существующего пользователя. ✅ Сделано (E9): секция `bootstrap:` с
`password_file`/`password_env`, создание только в пустом хранилище и только на `redb`, отказы на
пустом пароле, DN вне базы и DN, равном базе; `docs/ub-log.md` §36.

Диагностика для оператора переводится (`locale:`, `RUST_REST_LDAP_LOCALE`, `LANG`, файл
`locale/<tag>.yaml`); текст на проводе остаётся английским — `docs/ub-log.md` §30.

Опасные настройки (`AllowDangerousSettings`, `bind.AllowUnencryptedBind`,
`passwords.AllowedWeakHashes`, `AllowPlainHttpRest`) принимают фразу `Yes I know this is bad idea`,
а не `true`; без мастер-фразы наличие любой из них роняет старт — `docs/ub-log.md` §27.

Дополнительно сделано вне нумерации: локальный патч `rasn-ldap` (`vendor/`, коды RFC 4511
118–123) — без `assertionFailed` (122) assertion control неотличим для клиента от общего отказа;
подробности и порядок снятия патча — `docs/rasn-ldap-patch.md`.

Зависимости, которые нельзя нарушать: A1 раньше всего (иначе нечего проверять снаружи); B1 до B2
(запись должна быть аудируемой сразу); B5 после B4 (схему проверять на создании, а не только на
изменении); B7 после B4 (целостность проверяется на удалении); C1 после B5 (публиковать нечего,
пока нет реестра схемы); D1 в конце фазы C (мерить имеет смысл законченный сервер); F1 после A1
(клиенту нужен живой слушатель); F2 после C2 (флаги `-S` и `-E vlv` без сортировки на сервере не
проверить); F3 после E7 (читатель LDIF — обратная сторона уже написанного писателя); F4 после C3
(`ldapwhoami` и `ldappasswd` отвечают на расширенные операции); F5 после E7; D3 после F (README
описывает команды, которые есть).

## Что сознательно не делаем

- **AD-эмуляция уровня контроллера домена** (DRS, MS-NRPC, SYSVOL): отдельный продукт, а не фасад
  над LDAP. Bind по билету Kerberos и AD-совместимая схема сделаны (C8) — это не то же самое, см.
  раздел «Kerberos: границы и цена» ниже.
  **Про DRS отдельно, решением заказчика:** `GetNCChanges` и связанные атрибуты нужны ровно для
  одного — чтобы в нашем домене стояли контроллеры домена Microsoft. Этого не планируется, значит
  DRS не нужен, и «недоделанность» здесь не долг, а граница продукта. Репликация между нашими
  узлами идёт по RFC 4533 и слиянием по значениям (уровни 1–2), и ей DRS не мешает и не помогает.

## Члены домена Windows: что нужно и чего у нас нет

**Постановка заказчика:** контроллеры Microsoft в нашем домене не нужны, а **рабочие станции и
серверы Windows — нужны**. Это разные требования, и отказ от DRS второе не закрывает: DRS — про
репликацию между контроллерами, а вступление машины в домен идёт другими протоколами. Ниже —
честный список, потому что «Kerberos-bind работает» здесь не означает «машина вступит».

Порядок — по зависимости: без первого пункта остальные бесполезны.

1. **KDC у нас нет вовсе.** Есть только принимающая сторона: разобрать `AP-REQ`, проверить билет
   ключом сервиса, собрать `AP-REP`. Машина при вступлении и при каждом входе получает TGT
   (`AS-REQ`/`AS-REP`) и служебные билеты (`TGS-REQ`/`TGS-REP`) — их выдавать некому. Это самая
   крупная часть работы: ключи `krbtgt` и компьютерных учёток, генерация PAC с подписью KDC,
   политика времени жизни билетов, `kpasswd` для смены пароля учётки. Оценка — недели, а не дни.
2. **DNS с SRV-записями.** Windows ищет контроллер по `_ldap._tcp.dc._msdcs.<домен>`,
   `_kerberos._tcp.<домен>`, `_kpasswd._tcp`, `_ldap._tcp.<сайт>._sites...`. Без них `net join`
   отвечает «не удалось найти контроллер домена», и это самая частая причина отказа, которую
   принимают за проблему Kerberos. Вариант — BIND с DLZ на наше дерево (обсуждался), вариант —
   собственный минимальный ответчик SRV/A.
3. **CLDAP ping (UDP 389).** `DsGetDcName` шлёт поиск по rootDSE без установления сессии, и Windows
   пользуется этим путём первым. У нас слушатель только TCP; UDP-порт не открыт, и запрос молча
   теряется — обнаруживается как «контроллер не отвечает», хотя LDAP по TCP работает.
4. **MS-NRPC Netlogon.** Защищённый канал машины: `NetrServerAuthenticate3`,
   `NetrServerPasswordSet2` (смена пароля учётки), `DsrGetDcName`. Именно этим `net ads join`
   ставит пароль компьютерной учётки, а машина потом поддерживает его сама раз в 30 дней. Без этого
   вступление либо не завершается, либо машина отваливается через месяц.
5. **SMB (445) с шарами `NETLOGON` и `SYSVOL`** — нужны не для вступления, а для входа в домен и
   групповых политик. Машина без SYSVOL вступит, но политики не получит.

**Что у нас уже есть и пригодится:** rootDSE по TCP с `namingContexts` и `supportedCapabilities`,
класс `computer` (`1.2.840.113556.1.5.5`) и `userAccountControl` в AD-расширении схемы,
`userPrincipalName`/`sAMAccountName`, bind по билету, `memberOf`. То есть **словарь** машины в
каталоге есть; нет **служб**, которые этот словарь наполняют и обслуживают.

**Вывод для планирования.** «Windows-машины в домене» — это отдельный продукт объёмом с нынешний,
и начинать его надо с KDC, а не с Netlogon: контроллер без KDC не выдаст машине ни одного билета.
Порядок работ: KDC (1) → DNS (2) → CLDAP (3) → Netlogon (4) → SMB/SYSVOL (5), каждый шаг проверяется
настоящей машиной, а не тестом. До этого сервер остаётся LDAP-каталогом с Kerberos-bind для
приложений (`sssd`, веб-сервисы), и это надо называть именно так.
- Мультимастер-репликация: модель «несколько серверов читают один источник» уже работает;
  Content Sync (RFC 4533) — кандидат после C5, не раньше.
- X.500-ACI ApacheDS и `sock`/`dnssrv`-бэкенды OpenLDAP: сложность без выгоды для нашей задачи.
- **Отказ от tokio.** Обсуждалось и отклонено числом: tokio тянет 6 крейтов из 488 (1,2% дерева),
  C-кода не тянет вовсе, а плотность `unsafe` (9,9 на 1000 строк) — свойство любого рантайма над
  `epoll`, не выбор библиотеки: у `mio` под ним 11,5, у `smol`/`monoio`/`glommio` будет столько же.
  Замена стоит переписывания 128 `async fn` в 16 файлах и потери лёгкости соединений (поток на
  клиента при 10 тыс. клиентов — это ~160 МБ стеков).
- **Блокировка после неудачных bind.** Нет и не планируется: политика, которая при атаке на чужой
  аккаунт отрезает владельцу доступ. Место такой защиты — обратный прокси, а не каталог.
- **mTLS и HTTP/2** для служебных маршрутов: пять статических путей не нуждаются ни в том, ни в другом.
- **Репликация через raft** — рассмотрено и отложено (D19). Доводы против, по убыванию веса:
  кворум требует трёх узлов (два теряют доступность записи при потере любого), а типовое
  развёртывание — один сервер; машина состояний обязана быть детерминированной, а `argon2id` с солью
  даёт на двух узлах разные хеши одного пароля, и `entryCSN` считается по стенным часам — оба
  результата должны идти в лог, а не вычисляться на реплике; линейаризуемое чтение raft даёт только
  на лидере, а каталог читают больше, чем пишут; REST-бэкенд живёт в чужом сервисе, и консенсус над
  нашим представлением чужих данных не гарантирует ничего. LDAP-традиция реплицируется не
  консенсусом: syncrepl в OpenLDAP, multi-master с CSN в 389 DS.

## Фаза F. Свои утилиты `ldap-utils`

Зачем свои, а не пакет: `ldapsearch`/`ldapadd` нужны и оператору, и тестам, а `openldap-utils` в
образе — это сборочная зависимость от C (`libldap`, `libssl`), которой в проекте нет ни в рантайме,
ни в сборке. Свой клиент стоит дешевле, чем кажется: `src/ldap/codec.rs` уже кодирует и разбирает
`LdapMessage` в обе стороны, поэтому утилита — это транспорт, разбор флагов и LDIF, а не второй
протокол.

Граница, которую нельзя переходить: **свой клиент не может быть единственным судьёй правильности
сервера.** Эталонные прогоны `openldap`-утилитами (они есть на хосте) остаются в определении
«готово», а вторая независимая реализация протокола для перекрёстной проверки — `gorestldap`
(`~/DevOps/3part/gorestldap`, Go, без C): свои утилиты против чужого сервера, чужой `ldapsearch`
против нашего.

Имена бинарей совпадают с OpenLDAP намеренно (`ldapsearch`, `ldapadd`, …): команды оператора и
примеры в README не должны меняться. Конфликт с системным пакетом решается порядком в `PATH` образа,
а не префиксом в имени.

- SASL/GSSAPI/Kerberos и полный `ldap.conf`/`~/.ldaprc`: только флаги и переменные `LDAP*`; AD-стек
  в планах не значится (см. «Что сознательно не делаем»).
- `-M` (ManageDsaIT) и `-O` (proxyAuthz) — до C5, вместе с referral-бэкендом: без него управлять
  нечем.

## Kerberos: границы, цена и что из этого нам нужно

Разбор всех четырёх оставшихся пунктов линии C8, с ценой и условием возврата — чтобы отложенное
не выглядело забытым. Порядок — по отношению «польза / цена».

### PAC — проверка утверждений KDC. **Сделано (ub-log §107).**

Что даёт: авторизация по членству в AD **без локальных записей**. Добавили человека в группу в
AD — он получил права здесь; каталог руками никто не правит. Без PAC группы приходится вести у
себя, а AD остаётся только источником аутентификации.

Цена оказалась низкой, и разбор это предсказал верно: в вендоренном `vendor/rskrb5/src/pac.rs`
(2490 строк) уже были `Pac::parse`, `verify_server_checksum`, `ad_credentials` и готовые SID групп.
Написана оказалась ровно политика — `src/pac_policy.rs`: три режима (`ignore`/`verify`/`require`),
соблюдение срока логона с включающей границей и трактовкой «никогда» как сентинела, разрешение
групповых SID по `objectSid` в DN с передачей их в `Identity`/`Requester` (правило `group=` теперь
спрашивает одно — держит ли сессия группу). **Что не проверяется и не может:** подпись KDC над PAC
(она под ключом `krbtgt`, которого сервис не держит); проверяется подпись сервиса. **Что не
сделано:** channel binding, и живого AD-KDC для `verify`/`require` под рукой нет — проверено
юнит-тестами на копии PAC-структуры.

Когда: как только понадобятся права по группам AD. Сейчас проверка выключена осознанно (opt-out):
решения принимаются по записи и ACL, и сервис, который групп AD не знает, не должен от них
зависеть.

### FreeIPA не вводит Windows-машины в свой домен — и это важно для нашей постановки

Распространённое мнение, что FreeIPA (на 389 DS) позволяет вводить Windows-машины в домен,
неверно, и её собственные design-документы это фиксируют. `ipa-adtrust-install` настраивает Samba с
passdb-модулем `ipasam`, и получается контроллер домена **традиционного типа (Windows NT)**, а не
AD DC. Перечень ограничений из документации дословно: роль традиционного DC не реализует AD DC;
схема LDAP отличается от AD; DIT не тот, которого ждут AD-клиенты; **Global Catalog не
предоставляется**; и `ipasam` не умеет создавать компьютерные учётки по запросу Samba — поэтому
`netadsjoin` (ввод машины по-AD-шному) не может создать учётку, а `netrpcjoin` не работает из
членов домена IPA.

FreeIPA делает ровно одно: **cross-forest trust к настоящему AD**. Windows-машины входят в AD, а IPA
получает их пользователей и группы через доверие. Отсюда вопрос делится на два, и они стоят
несопоставимо.

**Путь A — Windows входят в AD, мы доверяем AD** (то, что делает FreeIPA). Чего не хватает нам:

| что | у FreeIPA | у нас | цена |
|---|---|---|---|
| проверка PAC | SSSD + idmap | парсер уже есть в `vendor/rskrb5/src/pac.rs` | 1–2 дня |
| отображение SID ↔ UID/GID | `sss_idmap`, sidgen-плагины | нет | 3–5 дней |
| объект доверия (TDO) в `cn=ad,cn=trusts` | `ipa trust-add` | нет | 3–5 дней |
| кросс-реалм Kerberos (referrals, межреалмовые `krbtgt`) | есть | нет: реалмы не связаны | 5–7 дней |
| MS-LSAD/LSAT и MS-NRPC поверх SMB `IPC$` | Samba | нет, SMB-сервера нет вовсе | недели |

Первые четыре строки дают **вход AD-пользователей к нашим LDAP/REST-ресурсам по GSSAPI**, без SMB и
без winbind. Пятая нужна, только если Windows-машины должны ходить к нам за SMB-ресурсами.

**Путь B — наш сервер сам становится контроллером домена.** Не хватает: SMB-сервера с шарами
`NETLOGON` и `SYSVOL` (без них ввод машины не начинается и GPO не работают); MS-NRPC Netlogon —
защищённый канал, создание и **ротация пароля компьютерной учётки** (на этом и спотыкается
`ipasam`), плюс `DsrGetDcName`, которым Windows ищет DC; полной AD-схемы и DIT с разделами
`CN=Configuration` и `CN=Schema`; Global Catalog на 3268 (без него не разрешаются универсальные
группы); DRS; AD-специфики Kerberos (генерация PAC, `msDS-KeyVersionNumber`, AD-формат солей, FAST,
RC4 для старых клиентов); GPO и репликации SYSVOL. Это Samba 4 AD DC — продукт двадцати лет, а не
фича. **Не идём этим путём.**

### Сколько стоит путь B на самом деле: что реализовала Samba 4

Samba 4 — единственная открытая реализация, которая **действительно** вводит Windows-машины в домен
(в отличие от FreeIPA выше). Поэтому она и есть честная мерка для пути B: не «сколько нам осталось»,
а «сколько это заняло у тех, кто это сделал». По их собственной документации (HOWTO, FAQ, статус).

**Что работает в продакшене** с версии 4.0 (2012), на функциональном уровне Windows Server 2008 R2:

- **Kerberos KDC** — встроенный (Heimdal); MIT KDC через `--with-system-mitkrb5` — экспериментально
  с 4.7;
- **LDAP-сервер как бэкенд AD** — встроенный, и только он: подставить OpenLDAP нельзя, для этого
  пришлось бы транслировать схему в рантайме (в FAQ названо главной причиной отказа);
- **DNS-сервер** — обязательная часть: Windows ищет контроллер домена по DNS;
- **SMB (SMB2/3)** и шары `NETLOGON` и `SYSVOL`;
- **MS-NRPC Netlogon** — защищённый канал, **создание и ротация пароля компьютерной учётки**,
  `DsrGetDcName`. Именно это делает `net ads join` работоспособным, и именно этого нет ни у FreeIPA,
  ни у нас;
- **генерация и подпись PAC** — авторизация по группам AD из коробки;
- **DRS-репликация** между DC (`GetNCChanges`), включая связанные атрибуты;
- **схема AD** (по умолчанию 2012 R2 с 4.11), **FSMO-роли**, сайты и подсети, парольные политики;
- **GPO**: файлы в SYSVOL, с ними работает штатный GPMC; Samba ничего не транслирует.

**Чего нет и через двенадцать лет** — из их же FAQ и списка пропусков:

- **репликации SYSVOL нет**: «It's currently not implemented», рекомендуют `rsync` между DC. Значит
  два контроллера домена расходятся в групповых политиках, и это ручная работа оператора;
- **доверие не доделано**: «Samba can be trusted, but can't trust yet», с оговоркой самих авторов,
  что работающие части — «a partial development that just happen to be in our released versions».
  Для нас это прямой вывод: доверять AD через Samba нельзя, это не путь A;
- нет **DFSR**, корзины (recycle bin), **ADWS / AD PowerShell**, **DCOM / WMI** — перечислено как
  «noticeable omissions»;
- функциональный уровень выше 2008 R2 — с 4.19 «still a work in progress», в продакшене не
  рекомендуется;
- репликация с внешним LDAP невозможна и не планируется.

**Вывод, ради которого это записано.** Разница между Samba и нами не в объёме кода, а в
направлении:

| | Samba 4 AD DC | мы |
|---|---|---|
| LDAP | AD-образный, свой, не подменяемый | общий LDAP, AD-совместимая **схема-подмножество** (C8) |
| Компьютерные учётки | создаёт и ротирует по MS-NRPC | нет |
| SMB, SYSVOL | есть | нет и не планируется |
| Репликация | DRS, без SYSVOL | RFC 4533 + слияние по значениям (уровни 1–2) |
| Клиенты | Windows-машины входят в домен | Linux по SSSD, приложения по LDAP и REST |

Чтобы «ввести Windows-машину», нужен не один недостающий протокол, а весь стек: SMB с `IPC$`, LSA,
Netlogon с ротацией пароля, схема и DIT AD, Global Catalog, DRS. Двадцать лет работы дали это — и
всё равно без SYSVOL и без доверия. Наша задача другая: идентичность и права для Linux и приложений.
Поэтому **путь B не начинаем** ни в каком объёме: половина пути B не даёт ни одного лишнего клиента.

**Решение:** Windows входят в AD (настоящий или Samba-AD), мы доверяем AD по Kerberos — путь A,
первые четыре строки. Порядок: PAC → SID в UID/GID → объект доверия → кросс-реалм Kerberos.
Итог: AD-пользователь берёт билет в AD, предъявляет нам, мы проверяем PAC и даём права по группам
AD — каталог руками никто не правит.

### Включение машин в домен — **Linux и Windows это два разных проекта**

- **Linux — работает уже сейчас** (с C8): SSSD против нашего LDAP + Kerberos. Нужны записи DNS
  `_ldap._tcp` и `_kerberos._udp`, SPN `ldap/<host>` (keytab так и устроен), TLS с сертификатом на
  правильное имя, AD-совместимая схема (есть). Это **конфигурация и проверка**, не разработка.
- **Windows — не работает, и LDAP+Kerberos тут не помогает.** Ввод машины в домен требует
  **MS-NRPC** (Netlogon: защищённый канал, пароли компьютерных учёток, их смена) и **SYSVOL** для
  групповых политик. Ни того, ни другого нет; DRS их и не заменяет — разные протоколы для разных
  задач.
  Вывод, который стоит принять прямо: если нужен «один домен для Linux и Windows», честнее взять
  Samba-AD или настоящий AD, а этот сервер оставить LDAP/REST-фасадом идентичности. Выращивать
  контроллер домена из LDAP-сервера — месяцы работы ради копии того, что уже есть.

### SASL security layer (integrity / confidentiality). **Не делать.**

Цена: 3–5 дней. Криптография уже есть — в `vendor/rskrb5/src/spnego.rs` лежат
`new_initiator_sealed`, `encrypt_payload_with_confounder`, `decrypt_payload`, `is_sealed`, то есть
wrap по RFC 4121 с конфиденциальностью написан. Не хватает трёх вещей: объявить слой в маске
(сейчас в `sasl_bind.rs` жёстко `NO_LAYER`), обернуть **каждое** последующее сообщение в
4-октетный префикс длины (RFC 4422 §3.2) и вести окно повторов. Риск не в криптографии, а в
разметке потока — это правка пути чтения и записи соединения.

Почему не делать: даёт то же, что TLS, но уже (только LDAP, без защиты других протоколов), а
клиенты просят его редко — Windows LDAP живёт на TLS, SSSD и Java настраиваются на TLS. Условие
возврата: клиент, который **умеет только** SASL-слой, или требование «шифрование без сертификата».

### authzid (прокси-авторизация). **Не делать.**

RFC 4422 §3.7: клиент говорит «аутентифицирован как X, действуй как Y». Нужно инструментам
администрирования и S4U, где сервис действует от имени пользователя. Цена — 2–3 дня, и это не код,
а политика: кто кому вправе это сказать. Ошибка здесь — обход ACL.

Сейчас authzid принимается и **не исполняется**, и это правильный выбор: молча проигнорированная
просьба безопаснее исполненной. Условие возврата: инструмент, который без этого не работает.
Заодно это согласуется с общим правилом проекта: несделанное объявляется, а не имитируется.

### Channel binding (CBT). **Отложить до первого Windows-клиента.**

Что это: привязка билета к TLS-каналу — сервер считает хеш своего сертификата
(`tls-server-end-point`, RFC 5929), клиент вкладывает его в аутентификатор. Защищает от того, что
билет, перехваченный в одном TLS-соединении, предъявят в другом (MITM-прокси), — **не** от кражи
билета как таковой.

Цена 3–5 дней, и настоящая цена не в коде, а в проверке: нужен **Windows-клиент**, у которого
включён EPA / «LDAP signing». Без него изменение непроверяемо, а непроверяемое изменение
безопасности хуже отсутствующего — оно выглядит сделанным.

### DRS (MS-DRSR). **Не наша задача.**

Протокол, которым контроллеры домена реплицируют друг другу разделы каталога целиком, включая
секреты, SID-историю и связанные значения; им же делают миграции (`GetNCChanges`). Нужен только
для сосуществования или репликации **с настоящим AD DC**. Для «включить машины в домен» — не нужен
вовсе. Цена — месяцы; это самая тяжёлая часть того, что делал Samba 4.

## Что осталось и почему

Ни одного пункта плана в состоянии «не начато» нет. Счёт по таблицам, посчитанный скриптом по
отметкам, а не на глаз: **53 сделано (✅), 0 сделано частично (🟡), 2 решено не делать (❌ — D15
axum и D19 raft, оба с причиной и условием возврата)**. Прежняя редакция этого абзаца называла
«58 ✅» — число было завышено на пять: часть отметок жила в прозе, а не в строках таблиц, и в
пересчёт не попадала.

Отдельно, потому что в таблицу не вписано: **D22 (потолок памяти и частичный кеш)** закрыт по
слоям 1–2 (§103 лимит, §106 кеш записей), слой 3 (скелет под потолком без кеша) не начат и в
таблицу не вносился; его состояние — в разделе D22 ниже.
Ниже — то, что сознательно вынесено за границы, с причиной, чтобы это не выглядело забытым.

- **Старт на трёх миллионах: 216 с → 5,18 с** (ub-log §104–§105) — цель «отвечать через 30 секунд»
  взята с запасом. Сделано: решение о снимке перед чтением стора, файловый формат с таблицей
  смещений и отображением в память (один задокументированный `unsafe`, крейт переведён на `deny`),
  скелет вместо записей (запись поднимается при ответе), и `Table::len` вместо чтения всего стора в
  bootstrap. Осталось тяжёлым и названным: **первый старт после импорта — 722,8 с на 3M** (82 с
  построения индекса и ~10 минут на запись снимка под свопом), это путь импорта, а не перезапуска;
  второй старт — 5,18 с.
- **Путь записи: 2,8 с → 33 мс на миллионе** (ub-log §100). Счётчик записей заведён, но главное
  было не в нём: `main` держал лишний `Arc` на каталог, `server` — снапшот на время обработки
  правки, а проверка уникальности обходила весь каталог. Всё три копировали каталог или читали его
  целиком на каждую запись; ответы при этом были верные, поэтому ни один тест корректности этого не
  видел. Отдельным следствием: `snapshot_rewrite_due` читал блоб снимка на каждой записи (164 мс) —
  теперь размер и номер в памяти. **Правило на будущее: замер на настоящем размере — часть шага, а
  не отчёт после него.**
- **D22 — ограничение памяти и частичный кеш базы в памяти. Принято к работе.**
  Почему сейчас: у сервера нет никакого потолка. На трёх миллионах записей рабочий набор —
  **7,6 ГБ** (3,2 ГБ резидентно + 4,4 ГБ в свопе), и сервер спокойно уводит машину в трэшинг:
  старт читал **62 ГБ** со свопа, процесс стоял в состоянии `D`, порт не был открыт. Ограничение
  должно быть нашим решением, а не решением ядра о том, кого вытеснять.
  **Числа, на которых проект стоит** (1 млн записей, тот же стенд): стор 4,18 ГБ, снимок индекса
  **197 МБ** (197 байт на запись), резидентный каталог ~3,2 ГБ. То есть **записи дороже индекса в
  двенадцать с лишним раз** — значит кешировать надо записи, а постинги держать целиком.
  Что делать, по слоям:
  1. **`limits.memory_bytes` — сделано** (ub-log §103). Считается по `/proc/self/statm` (размер
     страницы читается, а не предполагается), принимает `16G`/`16GiB`/`512M`/байты, при превышении
     **предупреждает и продолжает работать** — как решено. Заодно снят отпечаток данных со старта:
     45 секунд на трёх миллионах ради доказательства, которое уже даёт цепочка «счётчик + дельты».
     Измерено: миллион записей — `RssAnon` **6,1 ГБ** (то есть это наши данные, не страницы файла),
     значит три миллиона — порядка **18 ГБ**, и в шестнадцать они не помещаются. Потолок это
     показывает, но места не освобождает: для «влезть» нужен слой 3.
     Изначально предполагалось «соблюдает до выделения, а не после OOM» — **это отменено**: сервер
     предупреждает, а не отказывает.

     **Правило, которому подчиняется вся линия (сформулировано заказчиком):** не пытаться держать в
     памяти всё; поднимать в первую очередь то, что максимально ускоряет остальное; при недостатке
     памяти **отвечать медленнее, но отвечать** — «not ready» и «low mem» запрещены как ответы.
     Лучше ответ за 180 секунд, чем отказ. Отсюда два следствия, которые надо соблюсти в коде:
     (1) `limits.time_limit` не должен убивать деградировавший, но прогрессирующий поиск — значение
     по умолчанию остаётся «без потолка», а если оператор поставил маленький, это его выбор и он
     видит предупреждение о деградации; (2) ни один путь чтения не возвращает «ещё не готово» —
     промах кеша читает из стора и отвечает, пусть и дольше.
     **Превышение — предупреждение, а не отказ.** Сервер пишет, сколько нужно и сколько разрешено
     («на 3 000 000 записей рабочий набор ~7,6 ГБ, разрешено 4 ГБ: работаю с частичным кешем,
     ответы будут медленнее»), попадает в метрики и **продолжает обслуживать**. Причина прямая:
     недоступный сервер хуже медленного. Отказ в старте здесь защищал бы память ценой всего
     каталога, а оператор, у которого нет 8 ГБ, остался бы без службы вовсе — тогда как деградация
     по скорости его устраивает. Громким должно быть сообщение, не отказ.
     Тот же принцип — в предохранители: потолок ограничивает, что сервер держит резидентно
     (кеш записей, скелет), а не то, будет ли он работать.
  2. **`cache.entries_max_bytes` — сделано** (ub-log §106): LRU, ограниченный байтами, инвалидация
     в трёх путях записи, пять метрик, ноль выключает. Поиск читает из кеша, но **не наполняет** его.
     Замер на миллионе: повторный поиск по индексируемому атрибуту **0,038 против 0,045 мс** (15%),
     bind — без разницы (доминирует argon2id), память не выросла. Честная оговорка: при **холодном**
     сторе замер не снят (сброс страничного кэша требует root), и выигрыш там ожидается больше —
     это ожидание, а не измерение.
  3. Скелет вместо полного каталога: под потолком старт держит в памяти DN, `entryCSN` и
     проиндексированные атрибуты — этого хватает индексу и фильтру по индексируемым частям, — а
     сами записи поднимаются по требованию. Это и есть «частичное кеширование базы в памяти».
  Чего это не решает и в чём честность: фильтр по **неиндексированному** атрибуту в режиме скелета
  превращается в чтение всех попавших в область записей из стора. Это не регресс, это цена
  потолка, и она должна быть видна в логах и метриках (`ldap_cache_misses_total`,
  `ldap_cache_bytes`, `ldap_memory_limited`), а не обнаруживаться по времени ответа.
  Условие: сначала п.1 (потолок, предупреждение, деградация вместо отказа); затем п.2 —
  он и есть механизм деградации; п.3 — если понадобится каталог, который в память не влезает вовсе.
  **Порядок деградации фиксирован:** сначала перестаём наполнять кеш записей, потом вытесняем его,
  и только затем переходим на скелет — и каждый шаг вниз объявляется в логе один раз, а не на
  каждую запись.

### Память: что измерено и что осталось (ub-log §108)

Замер на миллионе, скелетный снимок, случайное чтение: **565 МБ RSS (450 МБ анонимной)**, медиана
**0,04 мс** на `(uid=…)`, потолок «индекс + десятая часть базы» укладывается (196 МБ индекса + 255 МБ
записей ≈ 451 МБ против 450 МБ факта). Старт 1,1 с.

**Незакрытое, по убыванию важности. Каждый пункт — с ценой, потому что без цены это список желаний.**

1. **Правка поверх отображённого индекса материализует всё.** `Index::add/replace/remove/apply_delta`
   при `mapped` вызывают `materialize()`: **одна правка = +1,14 ГБ** на миллионе (565 → 1703 МБ), и
   следующий старт после неё — 1,44 ГБ вместо 455 МБ, пока снимок не перепишется. Пока это так,
   потолок памяти остаётся предупреждением, а не границей: одно изменение учётки выводит процесс из
   бюджета. Лечится слоем дельт поверх отображения (правка пишется в журнал изменений индекса и
   применяется к файлу при перезаписи), а не материализацией. **Главный пункт.**
2. **Скелет держит проиндексированные атрибуты каждой записи** (~300 МБ на миллионе). Тонкий скелет
   (только DN и id) уменьшил бы это, но фильтр по неиндексируемому атрибуту тогда читает записи
   целиком — цена обмена названа, выгода мала: 300 МБ из 450. Делать только если понадобится бюджет
   меньше 400 МБ на миллион.
3. **Бюджет кеша не связан с потолком.** `cache.entries_max_bytes` — отдельная цифра (64 МиБ по
   умолчанию), а не «сколько осталось от `limits.memory_bytes`». Оператор, поставивший потолок,
   ждёт, что кеш займёт остаток сам.
4. **Холодный страничный кэш не измерен.** 0,04 мс — при тёплых страницах (стор читали импортом и
   стартом). Сброс требует root и задел бы соседние стенды, поэтому ожидание «на холодных будет
   больше» остаётся ожиданием.
5. **Нагрузка выше миллиона не проверялась после этих правок.** Числа на трёх миллионах (5,9 ГБ стора,
   455 МБ → ожидаемо ~1,3 ГБ скелета) — экстраполяция, а не замер.

- **Индексы поиска: края — упорядоченным индексом, `any` — n-граммами, tuple index — отложен.**
  Замер на миллионе (ub-log §89) и на трёх миллионах показал, где обрыв: `(cn=Ann*)` — 0,01 мс,
  `(cn=*12345*)` — 11 мс, `(cn=*zzz*)` — 0,00 с, а `(cn=*zz*)` — **230 с**, потому что шаблон короче
  трёх символов не содержит ни одной триграммы. Так устроены и эталоны: OpenLDAP индексирует
  подстроки блоками по 4 байта, 389 DS делает длину настраиваемой (`nsSubStrBegin`/`Middle`/`End`) и
  обрыв на коротких шаблонах есть у обоих. Вывод: триграммы не дефект, дефектом было отсутствие
  работающего `time_limit` (исправлено). **Следующий шаг — брать края у упорядоченного индекса:**
  `(cn=Ann*)` есть диапазон `[ann, anº)`, `(mail=*@skala-r.ru)` — префикс по перевёрнутому значению;
  хранения не требует, работает на одном символе, где n-граммы бесполезны по построению. Длину
  n-граммы сделать параметром, как в 389 DS: 4 дешевле по памяти, 3 селективнее — это выбор
  оператора. **Tuple index (как в AD) рассмотрен и отложен:** он отвечает на `(&(memberOf=A)(memberOf=B))`,
  а пересечение двух eq-постов — микросекунды; цена же квадратична по числу значений на запись
  (3 млн записей по 100 значений — 14,85 млрд пар, ≈2 ГиБ при одном бите на пост), и по `member`
  группы на 10 000 участников он прямо вреден — 50 млн пар ради запроса, которого не задают.
  Условие возврата: `memberOf` с вложенностью и развёртывание, где пересечения по большим группам
  станут узким местом. **Старт закрыт персистентностью** (ub-log §93): индекс складывается в redb с
  отпечатком (DN + `entryCSN` + план `indexes:`) и читается при следующем старте; ограничение —
  снимок валиден, пока данные не менялись, потому что id записи это её позиция. **Стабильные id сделаны** (ub-log §94):
  id записи больше не позиция, вставка и удаление применяются на месте, запись не читает стор.
  **Дельты сделаны** (ub-log §97): снимок переживает запись — стор пишет набор изменений на уровне
  записи под счётчиком, старт применяет их по порядку, дырка в цепочке даёт перестройку.
  **Порог перезаписи сделан** (ub-log §99): `indexes.snapshot_delta_bytes` — по умолчанию четверть
  снимка, не меньше мегабайта; перезапись идёт после ответа клиенту, на блокирующем потоке, и
  снимает покрытые ею дельты. Линия персистентности индекса закрыта целиком.
- **Fuzzing в CI — закрыт** (ub-log §98). Причина, записанная здесь, была неверной: фаззингу не
  нужны грамматики tree-sitter — они нужны инструментам измерения, которые разбирают Rust через
  python-пакет. Фаззингу нужны clang и `cargo-fuzz`, и не собиралось всё потому, что
  `fuzz/Cargo.lock` был написан до вендоринга `rskrb5`: без того же `[patch.crates-io]`, что у
  главного крейта, фазз-воркспейс брал `rskrb5` с crates.io, а его пин на pre-release `pbkdf2`
  несовместим с выпущенным. Теперь работает: `fuzz` в ночном расписании, шесть целей по минуте,
  находка отдаётся артефактом; локально `make fuzz-all` — 2,5 млн прогонов за 26 с на `dn`.
- **D8: мутатор по всему дереву — грамматики сняты с блокировки** (ub-log §98). Грамматики
  tree-sitter теперь запечены в образ измерения (24 МБ, только для чтения, работает без сети и без
  кэша на хосте), поэтому образ самодостаточен и годится для CI. Остался один блокировщик — цена:
  обход дерева ≈ 6 часов (D16). По файлу работает: `scripts/mutate.sh <файл>` (ub-log §65).
- **D21, уровень 1 — закрыт полностью.** Три пункта, которые здесь стояли, сделаны и проверены
  живьём на двух узлах (ub-log §89): журнал конфликтов (`replication.conflict_log`, JSON на
  конфликт, переживает перезапуск), живая проверка конфликта (два узла, один DN, разные
  `entryUUID` → `conflicts_total 1`, местная версия сохранена), TTL могильных плит по времени
  (`replication.journal_max_age`, считается из CSN, `0` отвергается).** Тот же прогон нашёл два
  дефекта, невидимых юнит-тестам: репликация отправляла `entryDN`/`subschemaSubentry` и не
  сходилась никогда, а данные от соседа попадали в стор без проверки схемы и оставляли узел
  неспособным к старту. Оба исправлены.
- **Уровень 2 мультимастера — слияние по значениям сделано** (ub-log §101). CSN теперь стоит рядом
  с каждым значением (`Attribute::value_csns`, проставляется в `stamp_write` только тем значениям,
  у которых штампа нет), и принятое от соседа изменение больше не пишется «как пришло»: содержимое
  записи становится слиянием с локальной версией. Решение уровня 1 перекрывается: версия, которая
  **старее** по `entryCSN`, но содержит значения, которых здесь нет, применяется — иначе уровень 2
  был бы мёртвым кодом. Слияние ничего не добавляет → запись не пишется (иначе переписывание на
  каждом опросе). Чистая функция `merge_attribute`/`merge_entries`, 26 тестов в `replication::`,
  включая ничью в одну микросекунду, которая разрешается номером сервера одинаково на обоих узлах.
  **Проверено живьём на двух узлах с перерезанной связью** (ub-log §101): связь через релей рвётся
  до правок, каждый узел правит вслепую; слияние включено — `alice, bob, carol` на обоих,
  выключено — `carol` теряется на обоих без единого конфликта. Первый вариант теста был отброшен:
  он проходил и без слияния. **Не сделано:** удаление значения на уровне значений (это решение, а
  не объединение).
- **Уровень 3** (векторы версий, как USN в AD) — только при десятках узлов.

**Чего сознательно не добавляю:** блокировка после неудачных bind (проверил — её нет; но это
политика, которая ломает доступ при атаке на чужой аккаунт, и её место в обратном прокси), mTLS,
HTTP/2 для служебных маршрутов.
