# Формат хранения, индексация, расширяемость и схемы

Документ фиксирует решения по шести связанным вопросам: как данные лежат на диске, как ищутся,
как сервер расширяется под чужие модели данных, как устроена схема, как её добавлять и отключать
на ходу, и что значит «переиндексировать». Числа — замер на текущем коде (release, один поток,
`tests/baseline.rs`; память — `tests/memory.rs`).

Состояние: E1 (обобщённая запись) и первый шаг E7 (`redb`) сделаны — см. раздел 9.

## 0. Замер отправной точки

Полный перебор при поиске (так работает сейчас): перебираются все записи в scope, к каждой
применяется фильтр.

| записей | equality, мс | presence, мс | substring, мс | только обход DN, мс |
|--------:|-------------:|-------------:|--------------:|--------------------:|
| 1 000   | 1.37         | 1.19         | 1.25          | 1.18                |
| 10 000  | 11.36        | 7.23         | 7.90          | 7.39                |
| 20 000  | 16.38        | 14.45        | 15.33         | 14.23               |

Стоимость записи: ~349 байт на значения и имена атрибутов, 336 байт структуры `User`, плюс
накладные расходы на `String`. То есть 20 тыс. записей — это ~7 МБ данных и ~16 мс на поиск, то
есть ~60 поисков в секунду на ядро при полном перебое. Для панели с десятком одновременных
пользователей этого хватает, для «адресной книги на 50 тыс.» — нет.

Вывод: индексы нужны не «вообще», а начиная с десятков тысяч записей и для конкретных типов
фильтров. Поэтому индекс — оптимизация, которая обязана давать ТОТ ЖЕ ответ, что и перебор
(раздел 2.4), и её стоимость измеряется, а не предполагается.

## 1. Формат хранения данных

Сейчас форматов два и оба «плоские»: JSON-файлы (`users.json`, `groups.json`) — источник, память —
`Directory` со `Vec<User>`/`Vec<Group>`. Запись (`modify`) перезаписывает весь файл через временный
файл и `rename`.

Что не так:

- Перезапись всего файла на одно изменение — O(n) на диске; при 20 тыс. записей это мегабайты на
  каждое изменение.
- Формат привязан к структурам `User`/`Group`, поэтому произвольный атрибут сохранить некуда
  (раздел 3).
- Обмена с другими каталогами нет: ни импорта, ни выгрузки.

### Решение: три слоя, у каждого своя задача

| Слой | Формат | Зачем именно он |
|---|---|---|
| Приём данных (бэкенд) | JSON | это контракт REST-источника, менять его нельзя без ломки интеграций |
| Локальное хранилище | redb (встроенная ACID-БД на чистом Rust) | одна запись — одна транзакция, без перезаписи файла целиком, без C |
| Обмен и выгрузка | LDIF | стандарт: импорт из OpenLDAP, `slapcat`-совместимый дамп, читаемо глазами |

Почему redb, а не альтернативы (проверено по crates.io 2026-11): `heed`/`lmdb-rkv` — обёртки над
LMDB, то есть C; `sled` в версии 1.0-alpha с 2024 года; `fjall` — LSM, хорошо для записи, но
сложнее в предсказуемости и с compaction-фоновыми задачами. `redb` — B-tree с MVCC, один файл,
чистый Rust, `forbid(unsafe_code)` в крейте.

**Ключ записи** — нормализованный DN (`dn.rs::normalize`), значение — та же JSON-сериализация, что
и в файлах: один формат всюду, отладка не требует отдельного инструмента. CBOR/bincode дали бы
скорость и размер, но усложнили бы эволюцию схемы (раздел 3) — для тысяч записей выигрыш не стоит
того.

**Порядок вставки задаётся не пользователем, а нами:** записи кладутся так, чтобы DN шли в
лексикографическом порядке предков. Тогда поддерево — это непрерывный диапазон ключей, и scope
превращается в range-scan, а не в фильтр по каждой записи. Это же свойство используется индексами
(раздел 2.2).

Бэкенды после этого:

| Имя | Что делает |
|---|---|
| `file` | читает два JSON-файла (совместимость с gorestldap), пишет через временный файл — остаётся для маленьких наборов и примеров |
| `redb` | постоянное локальное хранилище: чтение и запись по одной записи, ACID |
| `rest` | тянет JSON по HTTP (план, шаг C5) |
| `null` | пусто, только чтение |

## 2. Индексация

### 2.1 Какие индексы нужны

Набор взят из того, что реально спрашивают клиенты (и что умеет OpenLDAP через `olcDbIndex`):

| Тип | Для чего | Когда создаётся |
|---|---|---|
| `eq` | `(cn=admin)`, `(uid=jsmith)` | по конфигу на атрибут |
| `pres` | `(mail=*)`, `(objectClass=*)` | по конфигу |
| `sub` | `(cn=adm*)`, `(mail=*@example.com)` | по конфигу (3-граммы) |
| `ord` | `(uidNumber>=1000)`, server-side sort, VLV | по конфигу |
| DN | `entryDN`, base/one-level scope | всегда (по устройству хранилища) |

### 2.2 Представление

- Идентификатор записи — плотный `u32` внутри снимка. Номера выдаются в порядке DN, поэтому
  поддерево = непрерывный диапазон.
- Набор записей — `RoaringBitmap` (`roaring`, чистый Rust). Пересечение/объединение/дополнение —
  операции над битмапами, а не над списками.
- `eq`: `атрибут → (нормализованное значение → битмап)`. Нормализация — та же, что при сравнении
  значений (нижний регистр, кроме атрибутов с признаком `case_sensitive`).
- `pres`: `атрибут → битмап`.
- `sub`: 3-граммы значения → битмап. Фильтр `adm*` даёт кандидатов по граммам `adm`, дальше точная
  проверка. Для коротких значений (< 3 символов) — только `pres` и точная проверка.
- `ord`: отсортированный `Vec<(значение, id)>` на атрибут; диапазон — бинарный поиск.

### 2.3 Как вычисляется кандидатное множество

```
эквалайзер(фильтр) -> Option<Bitmap>      // None = индекс не применим
And: пересечение, Or: объединение, Not: дополнение в пределах scope
scope: диапазон номеров (base/one-level/subtree) пересекается с кандидатами
```

Индекс даёт НАДмножество ответа, после чего фильтр вычисляется на кандидатах обычной функцией
`filter::matches`. Значит, ошибка в индексе не может выдать лишнюю запись: она может только
пропустить — и именно это ловят тесты (2.4).

### 2.4 Как проверяется корректность

Индекс — оптимизация, поэтому инвариант один: **индексированный поиск отдаёт ровно то же, что
перебор**. Тесты:

1. **Эквивалентность на случайных данных**: генерируется каталог (детерминированным PRNG), набор
   фильтров всех поддерживаемых форм, ответ через индекс сравнивается с ответом перебора —
   включая порядок записей (клиенты на него опираются при пагинации).
2. **Каждый тип индекса проверяется отдельно**: пустой результат, одно совпадение, все
   совпадения, значение с отличающимся регистром, многозначный атрибут, отсутствующий атрибут.
3. **`--check-index`** (офлайн): проходит по всем записям, строит ответ перебором и через индекс и
   печатает расхождения — аналог `slapindex -c`.

### 2.5 Конфигурация и бюджет памяти

```yaml
indexes:
  default: [pres]                 # что индексируется, если атрибут не назван
  attributes:
    cn:        [eq, pres, sub]
    uid:       [eq, pres]
    mail:      [eq, pres, sub]
    memberUid: [eq]
    objectClass: [eq, pres]
    uidNumber: [ord]
```

Честная оговорка по памяти: `eq` на атрибуте с уникальными значениями (10 тыс. уникальных `cn`) —
это 10 тыс. битмапов по 8 байт плюс накладные расходы хеш-таблицы, порядка мегабайта на атрибут при
20 тыс. записей. Для уникальных атрибутов с фильтром «ровно одно значение» выигрыш всё равно есть
(11 мс → микросекунды), но бюджет надо считать: в отчёте по нагрузке (шаг D2) печатается размер
каждого индекса, и по умолчанию включается только `pres` плюс `eq` на тех атрибутах, по которым
реально ищут (`cn`, `uid`, `mail`, `objectClass`).

## 3. Расширяемость

Сейчас модель зашита: `User` и `Group` — структуры с фиксированными полями, атрибуты строятся
методом `attributes()`. Произвольный атрибут (например `telephoneNumber`, `departmentNumber`,
`employeeNumber` из чужой схемы) сохранить и отдать нельзя: его просто нет в структуре.

### Решение: запись как набор атрибутов, а не как структура

```rust
struct Entry {
    dn: String,                                   // нормализованный
    attributes: Vec<(String, Vec<Value>)>,        // порядок сохраняется
}
```

Что это меняет:

- `Directory` хранит `Vec<Entry>`, а не `Vec<User>`/`Vec<Group>`; `Entry::attributes()` больше не
  вычисляется, а лежит рядом.
- JSON пользователей/групп превращается в записи **адаптером** (`mapping`): сегодняшний формат —
  один из адаптеров, а не единственная модель. Появляется второй адаптер — «прямой»: JSON, где
  атрибуты уже перечислены (`{"dn": "...", "attributes": {"cn": [...], "mail": [...]}}`), что и есть
  расширяемость без перекомпиляции.
- Атрибуты получают тип из схемы (раздел 4), а не из структуры Rust.
- Сравнение, фильтры, ACL и проекция уже работают с `Attributes`, поэтому переезд затрагивает
  каталог, бэкенды и адаптеры, но не обработчики.

### Предел расширяемости, названный честно

Rust-плагинов без `unsafe`/ABI-контракта нет, поэтому «добавить свой бэкенд» означает «собрать
сервер с этим бэкендом». Расширяемость данных — через адаптеры и схему (без перекомпиляции),
расширяемость кода — через трейт `Backend` и `trait Mapping` в репозитории. Это записано в README,
чтобы не было ожиданий dlopen-плагинов, как у gorestldap.

## 4. Схемы

### 4.1 Схема как данные

Определения берутся в синтаксисе RFC 4512 (§4.1.2) — том же, в котором их пишут для OpenLDAP,
389 DS и ApacheDS:

```
attributetype ( 2.5.4.3 NAME ( 'cn' 'commonName' ) SUP name
    EQUALITY caseIgnoreMatch SUBSTR caseIgnoreSubstringsMatch
    SYNTAX 1.3.6.1.4.1.1466.115.121.1.15 SINGLE-VALUE )

objectclass ( 2.5.6.6 NAME 'person' SUP top STRUCTURAL
    MUST ( sn $ cn ) MAY ( userPassword $ telephoneNumber $ seeAlso $ description ) )
```

Разбор такой строки — отдельный модуль (`schema::parse`) с тестами на реальных определениях из
`core.schema`, включая многострочные, `$`-списки и OID-алиасы.

### 4.2 Что проверяется

| Проверка | Код результата при нарушении |
|---|---|
| обязательные атрибуты (`MUST`) присутствуют | `objectClassViolation` |
| атрибуты вне `MUST`/`MAY` отсутствуют | `objectClassViolation` |
| однозначный атрибут (`SINGLE-VALUE`) имеет одно значение | `constraintViolation` |
| структурный класс — один, и он не меняется | `objectClassViolation` |
| значение соответствует синтаксису (DN, Integer, Boolean, IA5, Octet String) | `invalidAttributeSyntax` |
| неизвестный атрибут или класс | `undefinedAttributeType` |

### 4.3 Где живёт

- `core` (минимум: `top`, `person`, `organizationalPerson`, `inetOrgPerson`, `posixAccount`,
  `posixGroup`, `organizationalUnit`, `domain`, `groupOfNames`) — в бинаре.
- Дополнительные файлы: `schema_dir` (каталог `.schema`-файлов, как у 389 DS).
- Публикация: `cn=schema` (`attributeTypes`, `objectClasses`, `ldapSyntaxes`) и `subschemaSubentry`
  (план C1) — клиенты и утилиты читают то же, чем сервер проверяет.

### 4.4 Режим строгости

Как `nsslapd-schemacheck` у 389 DS:

```yaml
schema:
  enabled: true
  mode: strict        # strict | warn | off
```

- `strict` — нарушение схемы отклоняет запись (по умолчанию).
- `warn` — запись проходит, в лог уходит предупреждение; нужно на время миграции чужих данных.
- `off` — проверка не выполняется (фасад над произвольным REST-источником, где `objectClass`
  произвольные). Публикация `cn=schema` при этом отдаёт то, что известно, и ничего не обещает.

## 5. Добавление и отключение схем на ходу

Как это устроено у соседей: OpenLDAP держит схему в `cn=config` (`olcSchemaConfig`) и принимает
изменения через `ldapmodify` без перезапуска; 389 DS читает файлы при старте и имеет плагин
Schema Reload; ApacheDS правит раздел схемы LDIF-ом.

### Решение для нас

1. **Источники**: встроенная `core` → файлы `schema_dir` → необязательная секция `schema: definitions:`
   в конфиге. Порядок важен: позднее дополняет раннее, переопределение существующего имени — ошибка
   (иначе непонятно, какое определение действует).
2. **Добавление без перезапуска**: `POST /schema/reload` (администраторский токен, как у callback)
   перечитывает `schema_dir` и подменяет реестр целиком так же, как перезагружается каталог —
   новый снимок, старый доживает свои запросы. Плюс `SIGUSR2` для того же действия (у нас уже есть
   `SIGUSR1` для данных).
3. **Изменение через LDAP**: `modify` на записи `cn=schema` (формат `olcAttributeTypes` /
   `olcObjectClasses`) сохраняет определение в бэкенд. Это потянет за собой право записи на
   `cn=schema` и переиндексацию (раздел 6).
4. **Отключение**: у каждого загруженного файла и у встроенных групп есть имя; `schema.disabled: [имя]`
   выключает набор. Отключение набора, на который ссылаются данные, **отклоняется** с перечнем
   записей: «в 12 записях используется `posixAccount`». Молчаливое отключение превращает живой
   каталог в невалидный, а ошибку потом ищут в клиенте.
5. **Отключение проверки целиком** — `schema.mode: off` (раздел 4.4), это отдельный случай: схема
   остаётся опубликованной, но не применяется.

Практическое следствие: добавление схемы — операция с данными, а не с процессом, поэтому она
попадает в журнал изменений (шаг C4) наравне с правкой записей.

## 6. Переиндексация

Индекс — производные данные от снимка каталога. Отсюда правила:

| Случай | Что происходит |
|---|---|
| Старт сервера | индексы строятся вместе со снимком (bulk), время пишется в лог |
| Перезагрузка данных (таймер, callback, `SIGUSR1`) | новый снимок со своими индексами; старый доживает открытые сессии |
| Изменение схемы | новый реестр + новый снимок: индексы по изменившимся атрибутам строятся заново |
| Изменение записи (`modify`/`add`/`del`) | инкрементальное обновление в новом снимке (в текущей модели — перезагрузка бэкенда) |
| Онлайн-переиндексация | `POST /reindex` (админ-токен): построить снимок заново, подменить, старый освободить |
| Переиндексация одного атрибута | `POST /reindex?attribute=cn`: перестроить только его карты |
| Офлайн-проверка | `rrl-directory --check-index`: сверить индекс с перебором, напечатать расхождения |
| Офлайн-перестройка | `rrl-directory --reindex [--dry-run]`: перестроить хранилище индексов без запуска сервера |

Почему «построить и подменить», а не «править на месте»: запрос никогда не видит наполовину
построенный индекс, а отмена/сбой переиндексации не оставляет каталог без индексов. Это то же
свойство, что у неизменяемого снимка каталога, и по той же причине.

Что печатается в лог и в `/metrics` (шаг C4): время построения по атрибуту, размер индекса в
байтах, число записей, доля фильтров, обслуженных индексом и ушедших в перебор. Без последней цифры
«индекс есть» ничего не говорит о его пользе.

## 7. Порядок работ (добавлено в план как фаза E)

Зависимость жёсткая: индексы строятся по атрибутам, а атрибуты появляются из схемы и обобщённой
модели записи. Поэтому:

| # | Шаг | Почему в этом порядке |
|---|---|---|
| E1 | Обобщённая запись (`Entry` вместо `User`/`Group`) + адаптер текущего JSON | всё дальнейшее опирается на произвольные атрибуты |
| E2 | Реестр схемы: разбор RFC 4512, встроенная `core`, проверка MUST/MAY/SINGLE-VALUE/синтаксисов, режимы strict/warn/off | даёт типам атрибутов смысл, нужный индексам и сортировке |
| E3 | Индексы `pres` и `eq` + конфигурация + тесты эквивалентности перебору | снимает 11 мс с поиска на 20 тыс. записей |
| E4 | `sub` (3-граммы) и `ord` (диапазоны, база для sort/VLV) | закрывает подстроки и будущий C2 |
| E5 | Переиндексация: онлайн-эндпоинт, `--check-index`, `--reindex` | эксплуатация без перезапуска |
| E6 | Схема на ходу: reload, отключение наборов, изменение через `cn=schema` | требует E2 и E5 |
| E7 | Бэкенд `redb` и LDIF-выгрузка | требует обобщённой записи из E1 |

Шаги B5 (проверка схемы при записи) и C1 (публикация `cn=schema`) из прежнего плана поглощаются
E2 и E6: делать их раньше обобщённой модели значило бы писать схему под зашитые структуры и
переписывать.

## 8. Что осталось непроверенным и будет измерено

- Время построения индексов на 10/20/50 тыс. записей и размер индексов в байтах (после E3).
- Выигрыш `sub`-индекса против перебора на подстрочных фильтрах: 3-граммы на коротких значениях
  могут оказаться дороже пользы — тогда остаётся `pres` + точная проверка.
- Поведение `ord` на числах против строк: в LDAP `uidNumber` сортируется как целое, а не как текст;
  это отдельное решение в E4, и оно должно быть закреплено тестом, иначе `(uidNumber>=100)` начнёт
  вести себя как строковое сравнение.
