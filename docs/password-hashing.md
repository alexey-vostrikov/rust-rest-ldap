# Парольные хеши: Linux, Windows, Kerberos, NTLM — и что из этого нужно LDAP-серверу

Документ отвечает на вопрос «какую библиотеку поддержки парольных хешей брать» и объясняет, почему
у этого вопроса нет одного ответа: Linux, Windows и Kerberos решают три разные задачи, и только
первая из них — «схема хранения пароля» в смысле LDAP.

## 1. Три разные модели, которые обычно смешивают

### 1.1 Linux: `crypt(3)` и подменяемый набор схем

Ядро модели — одна функция `crypt_r(password, setting)`, которая по строке `setting` (это и есть
хранимое значение) выбирает алгоритм, берёт из неё соль и параметры и возвращает новое хранимое
значение. Приложение не знает, какой алгоритм внутри: оно сравнивает результат с тем, что лежит в
`/etc/shadow`.

- Хранимый формат: `$id$params$salt$hash`, где `id` — алгоритм (`1` MD5, `5` SHA-256, `6` SHA-512,
  `2b` bcrypt, `y` yescrypt, `gy` gost-yescrypt, `7` scrypt).
- Реализация вынесена в `libxcrypt` (замена `libcrypt.so.1`); список «сильных» схем задаётся при
  сборке и на живой системе виден в `/etc/login.defs` (`ENCRYPT_METHOD`) и `hashes.conf`.
- Новые пароли в большинстве дистрибутивов сейчас идут в yescrypt (`$y$`) или в SHA-512-crypt
  (`$6$`); bcrypt и argon2 подключаются как политика, а не как умолчание.
- Фронтенд — PAM (`pam_unix`), который в свою очередь зовёт `crypt_r`. Для LDAP-входа ставится
  `pam_ldap`/`nslcd`/`sssd`: они читают `userPassword` из каталога, и если там `{CRYPT}$6$…`, то
  просто передают значение в `crypt_r`. Отсюда и происходит `{CRYPT}` в OpenLDAP.

Вывод для нас: «как в Linux» — это не один алгоритм, а **протокол с префиксом**, где хранимое
значение несёт всё нужное для проверки. Ровно эту же форму уже имеет `{SSHA}` в LDAP.

### 1.2 Windows / Active Directory: не хеш для проверки, а парольный эквивалент

AD не хранит значение, с которым можно сверить пароль способом «посчитать и сравнить» на уровне
каталога. Он хранит производные, из которых выводятся ключи протоколов:

- **NT hash** = `MD4(UTF-16LE(password))`, **без соли**. Это и есть «парольный эквивалент»:
  зная его, можно выдать себя за пользователя, не зная пароля.
- **LM hash** — наследие, отключён по умолчанию с Windows Vista / Server 2008.
- **Ключи Kerberos** выводятся из пароля с солью (см. 1.3), не из NT hash (кроме RC4).
- LDAP simple bind в AD не «сравнивает userPassword»: контроллер домена проверяет пароль через
  MSV1_0/NTLM или Kerberos, а `unicodePwd` доступен только на запись и только по зашифрованному
  соединению. Поэтому Samba AD DC отклоняет простой bind без шифрования сообщением
  `BindSimple: Transport encryption required`.

Вывод: NT hash нужен только для совместимости с NTLM/RC4-протоколами. Как схема хранения
«для проверки пароля из LDAP» он не нужен и опасен: соли нет, SHA-класс атак тривиален.

### 1.3 Kerberos: долговременные ключи, а не пароль

KDC не хранит ни пароль, ни его «хеш» в смысле `crypt`. Он хранит **набор долговременных ключей**,
по одному на каждый enctype, полученных функцией string2key:

- `aes256-cts-hmac-sha1-96` / `aes128-…`: PBKDF2-HMAC-SHA1, 4096 итераций, соль = realm + principal
  (RFC 3961/3962);
- `rc4-hmac`: ключ = NT hash, без соли — отсюда известная слабость «RC4 = парольный эквивалент».

Вывод: поддержать «krb» в LDAP-сервере нельзя частично. Либо сервер знает realm и principal
(то есть является KDC или его частью), либо Kerberos-ключи не хранятся вовсе. Для REST-фасада это
вне области, пока не появится режим AD-эмуляции.

## 2. Что реально делают LDAP-серверы

`userPassword` — атрибут с префиксом схемы. Набор схем у зрелых каталогов:

| Каталог | Схемы |
|---|---|
| OpenLDAP (ядро) | `{SSHA}`, `{SHA}`, `{SMD5}`, `{MD5}`, `{CRYPT}`, `{CLEARTEXT}` |
| OpenLDAP `pw-sha2` | `{SHA256}`, `{SHA384}`, `{SHA512}`, `{SSHA256}`, `{SSHA384}`, `{SSHA512}` |
| OpenLDAP `pw-argon2` | `{ARGON2}` (Argon2id с параметрами в самом значении) |
| 389 DS | `PBKDF2_SHA512` (умолчание в 12/13), `PBKDF2_SHA256`, `SSHA512`, `SSHA256`, `SSHA`, `SHA`, `SMD5`, `MD5`, `CRYPT`, `CLEAR`, `AES` (обратимая — только для отдельных сценариев) |
| ApacheDS | `{SSHA}`, `{SHA}`, `{SMD5}`, `{MD5}`, `{CRYPT}`, `{SASL}`, `{PBKDF2}` и парольная политика по draft-behera |

Примечательно, что 389 DS прямо документирует: «единственные безопасные схемы —
`PBKDF2_SHA256` (ныне `PBKDF2_SHA512`), при невозможности — `SSHA512`, всё остальное считать
небезопасным». И держит **обновление хеша при bind**: при успешном simple bind пароль в открытом
виде известен, поэтому сервер перезаписывает слабый хеш сильным (`nsslapd-enable-upgrade-hash`).

## 3. Схемы по существу

| Схема | Что внутри | Соль | Стойкость | Нужна нам |
|---|---|---|---|---|
| `{SSHA}` | SHA-1(pw + salt) + salt | да | устарела (SHA-1, быстрая) | да, только на чтение — совместимость с gorestldap |
| `{SHA}`/`{MD5}`/`{SMD5}` | без соли или с солью, быстрые | не всегда | небезопасна | только чтение |
| `{SSHA256}`/`{SSHA384}`/`{SSHA512}` | SHA-2 + соль | да | приемлемо, но быстрая | да, чтение и запись как совместимый вариант |
| `$5$`/`$6$` (SHA-crypt) | PBKDF-подобный, 5000 итераций | да | приемлемо | да, ради `{CRYPT}` для Linux-клиентов |
| `$2b$` (bcrypt) | Blowfish, cost | да | хорошо, но максимум 72 байта пароля | опционально |
| `$y$` (yescrypt) | memory-hard | да | хорошо, умолчание дистрибутивов | опционально |
| `{ARGON2}`/`{ARGON2ID}` | memory-hard, параметры в значении | да | лучшая на сейчас | да, как схема записи по умолчанию |
| `PBKDF2_SHA256/512` | PBKDF2, счётчик итераций в значении | да | хорошо | да, для совместимости с 389 DS/FreeIPA |
| NT hash | MD4(UTF-16LE(pw)) | **нет** | парольный эквивалент | нет (только в AD-режиме) |
| LM hash | DES-производная | нет | взлом за минуты | нет |

## 4. Крейты (без C)

| Нужно | Крейт | Замечание |
|---|---|---|
| Argon2 (id/d/i) | `argon2` | RustCrypto, `forbid(unsafe_code)`, параметры парсятся из PHC-строки |
| PBKDF2 | `pbkdf2` | RustCrypto, HMAC-SHA256/512 |
| scrypt | `scrypt` | RustCrypto |
| bcrypt | `bcrypt` | чистый Rust, `$2b$` |
| yescrypt | `yescrypt` | чистый Rust, 0.1.0 — сверять с эталонными векторами |
| SHA-2, SHA-1 | `sha2`, `sha1` | уже в проекте (`sha1` для SSHA) |
| MD4 (NT hash) | `md4` | нужен только в AD-режиме |
| Постоянное по времени сравнение | `subtle` | уже в проекте |
| Мультисхемный разбор | `pwhash` | удобно, но последний релиз 2021 — лучше разбирать самим по префиксам |
| `crypt(3)` целиком | `libxcrypt` через FFI | C-зависимость; не берём, `$5$`/`$6$`/`$y$` реализуются крейтами |

## 5. Рекомендация для rrl-directory

Разделить три роли, которые сейчас слиты в `src/ssha.rs`:

1. **Проверка (verify)** — принять всё, что встречается в реальных данных: `{SSHA}`, `{SHA}`,
   `{SSHA256}`, `{SSHA384}`, `{SSHA512}`, `{SHA256}`, `{SHA512}`, `PBKDF2_SHA256`,
   `PBKDF2_SHA512`, `{ARGON2}`, `{ARGON2ID}`, `$5$`, `$6$`, `$y$`, `$2b$`. Значение без префикса —
   отказ (в OpenLDAP это исторически «открытый текст», принимать нельзя).
2. **Запись (store)** — `ARGON2ID` по умолчанию (memory-hard, параметры в значении), `PBKDF2_SHA512`
   как совместимый вариант для стыковки с 389 DS/FreeIPA. `{SSHA}` не писать никогда.
3. **Обновление при bind** — как у 389 DS: если проверка прошла, а схема слабее целевой,
   перезаписать `userPassword` сильным хешем через бэкенд. Это единственный момент, когда пароль
   есть в открытом виде, и единственный способ поднять стойкость уже существующих данных без
   массового сброса паролей.

Чего не делать:

- **NT hash, LM hash, RC4-ключи** — не хранить и не вычислять. Это парольные эквиваленты; их место —
  AD-эмуляция, которая потребует и Kerberos (realm, principal, ключи по enctype), то есть
  отдельного режима, а не схемы в `userPassword`.
- **`{CLEAR}`/`{AES}`** (обратимые схемы 389 DS) — обратимая схема превращает утечку бэкапа в утечку
  паролей.
- **`{CRYPT}` через libxcrypt** — тянет C-библиотеку; нужные форматы (`$5$`, `$6$`, `$y$`) дают
  крейты.

Отдельно то, что нужно починить независимо от выбора схем: **сейчас `userPassword` попадает в
результат поиска**. В нашей модели атрибут не помечен операционным, поэтому `*` его отдаёт, и любой,
кто видит запись, получает хеш (`examples/file/users.json` — реальный `{SSHA}`). В OpenLDAP и 389 DS
доступ к `userPassword` закрыт ACL по умолчанию. Правильно: отдавать его только при явном запросе
имени и только для администратора (или владельца записи), а из `*` убрать.
